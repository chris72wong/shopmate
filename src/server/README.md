# Backend implementation handoff

The public v1 request/response shapes in `src/contracts/` are unchanged. The earlier implementation-status tables in PLAN.md and docs/API.md describe the former stubs; the routes now implement the behavior below.

- `POST /api/stores`, demo: existing fictional country-specific stores; no location lookup.
- `POST /api/stores`, live: country-restricted Google Geocoding followed by Places API (New) Nearby Search. Only country-allowlisted major grocery banners are eligible; the nearest returned branch per banner is retained. Real provider names, addresses, Maps links, straight-line distances and third-party attributions. All real stores have unavailable v1 pricing; a chain match never grants sample prices to a live journey.
- `POST /api/optimize`: explicit demo optimization works without credentials. Live sample-price optimization is rejected; use v2 for real quotes. The ID resolver validates country, grocery type, operating status and returned ID, and does not fabricate distances without an original search origin.
- `/api/v2/catalog`, `/stores`, `/pricing`, `/optimize`: implemented additive verified-price workflow. Exact reviewed Google/provider branch bindings, current Reef Loblaws-family CA pickup / Kroger-family US in-store observations, strict reviewed SKU/package mappings, full provenance, missing coverage and the existing deterministic engine. Own key/mappings are required; no live mappings or prices are invented. See [PRICING.md](../../docs/PRICING.md) for setup and actual test evidence.
- `GET /api/v2/deals?country=CA&province=ON|QC`: implemented public Bidou regional RSS. The actual ON reader passed its live network test. Deals remain attributed/dated, unknown branch/stock/expiry and never optimizer eligible.
- `GET /api/health`: discovery and optimization implementation flags are true. Missing credentials still return a structured 503; flags do not promise provider access or verified prices.

The frontend owner must keep illustrative-price / fictional-store / estimated-nutrition labels visible and render the official Google Maps logo and supplied third-party attributions. Public Terms/Privacy pages and deployment key restrictions/quotas remain live-launch requirements. No frontend files were changed during this backend task.

## Major-grocer selection and pricing handoff

`discovery/chains.ts` contains the country-specific banner allowlists and exact known name/format variants. Punctuation, accents and possessive owner-prefixed No Frills names normalize conservatively. Independent shops, warehouse clubs, specialty-only banners, pharmacies and fuel locations are excluded. Google country, grocery type, primary business type and operating status are checked at discovery and again during authoritative Place Details resolution. An invalid/unavailable selected store returns `422 invalid-request` with a `storeIds` detail and an instruction to choose other stores.

Eligible candidates sort by straight-line distance, then public store ID. One branch per internal banner identity survives; format variants share that identity, while corporate siblings such as Loblaws/No Frills/Real Canadian Superstore and Kroger/Ralphs remain separate. Existing public `google:<placeId>` IDs and all six `chainId` values are preserved; new banners keep `chainId: null`. No internal banner identity is added to the API. Radius controls and the one-to-three selection limit are unchanged.

The response notice includes **“Major grocery chains · nearest location per banner.”** The result is the nearest **returned** branch of each recognized banner among at most 20 candidates, not exhaustive coverage of every chain or branch in the radius. Empty results explicitly say other stores may exist. See the official [Nearby Search limits and ranking](https://developers.google.com/maps/documentation/places/web-service/nearby-search).

Google provides locations, not ingredient prices. Missing real pricing configuration remains separate work. V1/v2 shapes, error codes, attribution fields and illustrative/verified separation are unchanged. `/api/v2/pricing` provides the existing structured states below; frontend consumers should use the discriminants, not parse notice/message text.

| Response | Existing structured information | Frontend integration |
| --- | --- | --- |
| `200`, no usable offers | Each `data.stores` item is `unavailable`, with `reason: "unsupported-store"` for an unmapped branch or `"no-usable-offers"` after a successful query without usable products; no offers or total are invented | Stay on Stores when no item has `status: "available"` and a nonempty `offers` array; show the notice and actions to change stores, retry or explicitly open samples |
| `503 provider-not-configured` | Missing retailer credentials or product mappings for a configured branch; `error.details[].path` identifies the requested `storeIds.<index>` and `message` explains its failure | Stay on Stores; retain the chosen stores and display the configuration failure with recovery actions |
| `429 rate-limited` / `502 provider-error` | Existing error envelope, including per-selection `details`; upstream messages/keys/payloads remain private | Stay on Stores and allow retry or another selection |
| `200`, partial coverage | Usable sets retain `status: "available"`, `basis: "verified"`, actual offers and sorted `missingIngredientIds`; failed stores retain their own structured reasons; `notices` explains partial coverage | May continue with coverage visible; catalog coverage alone does not establish any particular basket's completeness |
| Later `200` optimization with `status: "infeasible", reason: "pricing-unavailable"` | Exhaustive catalog search found no fully priced plan; `minimumKnownCost: null`, exact pricing snapshot and no plan total | Show **“Ingredient prices unavailable”** and **“Choose other stores.”** Budget/dietary reasons keep their separate preference-editing actions |

An unmapped branch remains domain unavailability even when the global retailer key is absent; discovery success does not establish a supported pricing branch. A branch with no reviewed product mappings is unavailable before retailer calls begin. Invalid optional pricing configuration marks discovered stores unavailable without discarding successful Google locations; pricing requests still return the existing configuration error. Partial successes preserve requested store ordering and failures. The optimizer independently refreshes pricing, requires every ingredient including oil, and supplies comparable totals/savings only for complete same-currency, same-channel baskets.

This backend change does not edit frontend components or flow state. The frontend owner is responsible for the Stores gate, heading/button copy and navigation above. Synthetic tests cover the actual route responses that drive those states; no credentialed full retailer basket is claimed.

It reads regular prices only, preserves absent prices and unreviewed package labels, and never converts these observations into v1 offers. Required server settings: `KROGER_CLIENT_ID`, `KROGER_CLIENT_SECRET`; the optional test also needs `KROGER_PROBE_POSTAL_CODE`. **Instacart:** the [public nearby-retailer endpoint](https://docs.instacart.com/developer_platform_api/api/retailers/get_nearby_retailers) covers US/CA retailer organizations; it does not establish physical-branch SKU/package prices. No Canadian or cross-retailer verified pricing access is established here.

There were no configured credentials in this checkout, so no application-key provider requests were made. Public Reef browser trials successfully returned Loblaws/No Frills CAD and Kroger USD prices; Bidou public ON RSS was tested through the actual reader. These are not credentialed application end-to-end coverage. Google/Reef route composition uses synthetic upstream responses, not copied production fixtures. ## Deterministic optimizer

`optimization/engine.ts` exposes `optimizationEngine` and injectable `createOptimizationEngine`. Candidate space: every multiset of the requested number of eligible catalog recipes, including repeated recipes. Meal order does not affect the calculation. Deterministic repeated/diverse seeds precede lexicographic enumeration. The default limit is 20,000 unique combinations. Exhaustion yields `proven` or `infeasible` only within this catalog; a cap yields `best-found` or `incomplete`.

Each run fetches offers once per selected store. Recipe yields scale before ingredient aggregation; quantities keep canonical dry/drained/edible g/ml/each semantics. All listed ingredients, including oil, are priced. Missing/wrong-currency/unsupported offers make a store basket unavailable **without a total**. Complete baskets use full-package purchase cents. Multi-size packages use an exact integer covering knapsack; unsupported pathological precision/state spaces fail rather than pretending a truncated package solution is optimal.

Scoring revision `catalog-multiset-1`: cost-first strictly minimizes full purchase cents; high-protein can break equal-cost plan ties. Nutrition-first uses protein (70%) and fibre (30%) per serving, scaled to 40 g / 12 g for ranking, with small cost (.05), leftover (.03), and variety (.03) terms. Balanced weights are cost .55, nutrition .25, variety .10, leftover .07, reuse .03. High-protein adds a .15 protein ranking term outside cost-first. These are soft ranking scales, not dietary targets or guarantees. Leftover fractions are normalized per ingredient; grams, millilitres and counts are never summed as a waste weight. Ties use cost, recipe-ID multiset, then store ID. Store ties use cents then ID.

Ingredient reuse compares consolidated purchases with buying each meal's packages separately at the recommended store. Basket savings compare the identical requirements at another complete selected-store basket. Nutrition derives from consumed ingredient quantities, not purchased packages, and remains sample estimates.

## Verification commands

`npm run verify` runs lint, typecheck, all tests, production build and HTTP smoke checks. Tests cover synthetic Google success/error/empty/country/attribution/timeout cases, authoritative store resolution, package arithmetic and brute-force comparisons, hard constraints, currency, budgets, missing pricing, deterministic search and capped results, plus CA/US route journeys.

Network probes are opt-in: set `SHOPMATE_LIVE_SMOKE=1` and relevant shell credentials/configuration, then run `npx vitest run tests/backend-live.test.ts tests/pricing-live.test.ts`. They consume quota, do not log/store provider payloads, and do not replace a full credentialed basket verification. Skipped probes are not evidence of working live access. The pricing test also exercises the credential-free public Ontario feed.
